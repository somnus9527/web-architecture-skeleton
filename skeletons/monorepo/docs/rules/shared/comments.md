# Comment Rules

> 前后端共享规范。注释的目的是解释**为什么这样做**、业务约束来源和不明显的边界条件,而不是复述代码。
>
> 注:本文件合并自前后端两份 comments 规范。"简单代码是否必须写注释"已定档:**Service 层方法逐个必写注释;其他地方精简**(只解释 why / 约束 / 不明显处)。

## Code Comment Rules

### Applicability

1. 本规范默认适用于当前任务新增或修改的手写代码,包括但不限于:`js` / `ts` / `tsx`、Java、Vue SFC 的 `template`/`script`/关键样式结构、shell/构建/生成器/工具脚本、运行时接线代码。
2. 下列内容默认不强制补充注释,除非用户明确要求:第三方/vendor 代码、锁文件、二进制/图片/字体/音视频、纯数据文件(多数 `json`/`yaml`/`toml`)、外部工具自动生成且当前生成器不可控的文件。
3. 对于生成代码:生成器可控时优先改生成器;不可控或暂不支持时,必须在最终说明中明确缺失范围。

### General(why-not-what + 语言约定)

1. **注释力度两档:Service 层方法逐个必写;其他地方精简**(详见下方 Rubric)。
2. 业务注释统一使用**中文**,多行优先(便于编辑器悬浮展示);**技术机制和代码标识符保持英文**。
3. 注释必须解释职责 / 业务语义 / 边界 / 约束,不得只复述代码表面;禁止"处理数据""设置值""执行方法"这类低信息量敷衍。

### 注释粒度 Rubric

- **Service 层方法 [强制]**:后端 Application Service / Domain Service 的**每个方法**、前端 `service/` 的**每个 API 方法**,都必须有方法注释 —— 至少说明职责;涉及入参 / 返回 / 副作用 / 边界 / 幂等键 / 事务时补充。**不得因"简单"省略。**
- **复杂 / 高风险逻辑 [详细]**:复杂函数、通用能力函数(组合式函数 / 共享 hook / store / 请求封装 / runtime 接线 / 生成器 / 脚本 / 工具集 / 基础设施能力)、状态机、事务边界、幂等键来源、兼容 / 兜底分支 —— 多行说明功能 / 关键流程 / param / return / 副作用 / 边界。
- **类型契约 [按需详细]**:`interface` / `type` / 枚举 / 字段,涉及格式 / 枚举语义 / 可选条件 / 取值范围 / 单位 / 默认值时必须说明,不只重复字段名。
- **其他地方 [精简]**:简单、显然、命名自解释的代码**不强制**注释;只在 why / 业务约束 / 不明显边界处补一句。HTML / Vue template / TSX 仅在区块结构、条件 / 循环入口、核心交互、业务关键区加简要注释,装饰性 / 显而易见节点不加。

### TODO 与作者

- TODO 必须带 owner 或 issue 编号;owner 用你自己的标识(本地 git 账号 / 姓名),例如 `TODO(<your-git-name>): link ISSUE-123`。
- **不硬编码固定作者名 / `@author`**:作者以**每个人本地环境的 git 账号**为准(`git blame` / commit 记录追溯),不在文件头写死个人名。

### Anti-Patterns

- 注释和代码表达重复。
- 用注释掩盖复杂代码,而不是拆方法 / 改名。
- 注释写已失效的业务事实。

## Execution

1. 当前任务新增/修改的手写代码,结束前必须自检是否满足本规范;不满足不应直接结束任务。
2. 因更高优先级指令或生成器限制无法完全满足时,必须在最终说明中指出原因和缺失范围。
3. 项目规则与本文件同时生效时,默认以更严格者为准。

## Checklist

- [ ] 注释说明了原因 / 约束 / 风险,不是复述代码
- [ ] **Service 层每个方法都有注释**;复杂 / 高风险逻辑有完整说明;其他地方精简(简单代码不强制)
- [ ] TODO 有 owner(本地 git 账号);未硬编码 `@author` / 固定作者名
- [ ] 没有过期业务事实
